Постбек – це функціонал сповіщення системи аналітики (трекера) партнера про події на стороні партнерки. Сповіщення відбувається за допомогою надсилання запиту на URL постбеку. Події для відправлення постбеків пов'язані з гравцями, яких привів партнер.

Якщо партнер передає у своєму посиланні click_id, то після отримання події, коли для бренду/оферу налаштований шаблон постбеків, наша система відправить постбек за шаблоном.

Постбеки відправляємо методом запиту GET.

Поруч із шаблонами є кнопки редагування та переходу на сторінку логу постбеків по шаблону.

## 2. Створення/Редагування шаблону

2.1. Налаштування шаблону постбека починається з того, що партнер має скинути URL, за яким необхідно "відстукувати" постбек. Це URL його трекера.

Якщо трекер партнера – Keitaro, можна звернутися до спеціалізованого гайду з налаштування постбеків для Keitaro, АЛЕ попередньо прочитавши цей гайд.

Як налаштовувати постбеки для Keitaro? Відповідь за посиланням (https://help.aff.ltd/uk/admin-panel/postbacks-for-keitaro).

2.2. На сторінці клікаємо на кнопку "+ Додати шаблон постбеку": https://aff.ltd/admin/new/postback-urls/create

Для партнера можна додати набір URL-ів під кожен тип подій. Набір може бути додано по конкретному оферу, для всіх оферів певного бренду або по всім оферам для всіх брендів.

На сторінці обираємо партнера, бренд (продукт), за яким треба відправити постбеки.

Далі вибираємо офер, за яким "литиме" партнера. Можна вибрати всі офери або лише необхідні за запитом партнера (наприклад, якщо потрібні різні шаблони на різні офери).

Global postback – параметр, який іде першим у списку вибору для бренду. Його вибір означає, що при додаванні постбеку будуть вибрані всі бренди та всі офери.

Нюанси:

- Якщо при налаштуванні постбеку партнеру треба вибирати всі бренди, це не означає, що буде вибрано Global postback. Аби обралося налаштування Global postback, потрібно саме його вибрати в брендах;
- Якщо вибрати два бренди, а потім тільки офер для одного з вибраних раніше брендів, то лише за цією офером відправлятиметься постбек. У цьому випадку за іншим брендом, для якого не вибрали жодного оферу, система постбеки не відправлятиме.

2.3. На наступному етапі вибираємо подію, яку хочемо "відстукувати" та вставляємо URL від партнера.

Для відправлення доступні події:

- Реєстрація (REG);
- Перший депозит (FD);
- Повторний депозит (RD) – повторні депозити RD, FD у цій події не відстукуються.

Події для CPA та гібридних оферів:

- Кваліфікація (CPA Hold);
- Підтвердження (CPA Approve);
- Відмова (CPA Reject).

Події для REVSHARE та гібридних оферів:

- Дохід за RevShare (RS).

Список налаштованих подій можна переглянути при редагуванні шаблону постбека для партнера.

Нюанси:

** Якщо є два шаблони постбеків, один по конкретному оферу бренду та один по всьому бренду, то шаблон по конкретному оферу бренду має більший пріоритет. Його буде використано для гравців цього офера. Для Global постбека логіка працює аналогічно – у пріоритеті шаблон по конкретному оферу (або шаблон по конкретному бренду).

** Усі сповіщення приходять у хронологічному порядку: Реєстрація, Перший депозит, Повторний депозит тощо. Наприклад, відстук про перший депозит не може прийти до того, поки не прийшов відстук про реєстрацію.

** Подія "Повторний депозит (RD)" в основному використовується для відправлення івентів за RevShare (окрім Revshare amount – для цього є окремий івент). У випадку зі CPA/CPFD – після кваліфікації цей постбек перестає відправлятися.

** Якщо у партнера вказано пустий URL для події, то постбек створиться, але не відправлятиметься. Статус постбеку "Не буде відправлено".

** Подія "Дохід за RevShare (RS)" працює для оферів:

- REVSHARE;
- DYNAMIC_REVSHARE;
- CPA_BASELINE_REVSHARE;
- CPA_AGGREGATED_BASELINE_REVSHARЕ;
- CPFD + REVSHARE.

** "Дохід за RevShare (RS)" відправляється раз на добу (наприкінці доби), після нарахувань за RevShare.

** Для CPFD оферів відправляються лише ті гравці, які були кваліфіковані (по FD/RD постбекам).

2.4. Після додавання URL трекера партнера в потрібні події – необхідно замінити його змінні нашими макросами.

Під кожну подію партнер надає окремий URL.

2.6. Опис макросів:

- ##CLICK_ID## – ідентифікатор, отриманий від CPA партнера;
- ##POSTBACK_ID## – внутрішній ID постбеку. Додаткова змінна, завжди унікальна для кожного постбека. Допоможе партнеру отримати унікальне додаткове значення щодо певного івенту з однаковим click_id (наприклад, дохід за RevShare по одному й тому самому гравцю в різні дні);
- ##USER_ID## – ID запис в SiteUser (ID гравця на проекті);
- ##TRANS_ID## – унікальний ID гравця на платформі AMP;
- ##IP_REG## – IP реєстрації гравця (передається у форматі: IP повністю);
- ##GEO_REG## – країна реєстрації гравця (двохлітерне значення, наприклад: "NL" для Netherlands);
- ##FD_AMOUNT## – сума першого депозиту гравця;
- ##RD_AMOUNT## – сума повторних депозитів гравця;
- ##SITE_ID## – ID бренду;
- ##CPA_AMOUNT## – сума, нарахована партнеру за CPA офером;

Значення для макроса ##CPA_AMOUNT## завжди статичне. Для всіх подій за ним передається ставка за офером.

- ##SUB_ID## – сабайді (трекер рефкоду);
- ##SUB_ID_2## – додатковий множинний сабайді;
- ##SUB_ID_3## – додатковий множинний сабайді;
- ##SUB_ID_4## – додатковий множинний сабайді;
- ##SUB_ID_5## – додатковий множинний сабайді;
- ##RS_AMOUNT## – сума, нарахована партнеру за RevShare. Відправляється раз на добу, у момент створення нарахування за минулий день. Відправляється тільки для події "Дохід за RevShare (RS)”.
ВАЖЛИВО! Dynamic RevShare – дохід при зміні порогу динамічної ревшари – не довідправляється.

Макроси окремо доступні для копіювання за кліком. Опис кожного макросу виводиться при наведенні курсору на нього.

[image: https://d295evyo48.ucarecd.net/b3de7059-8111-44ba-b8ab-359fe615190d/screencast_2025-11-11_12-35-49.gif]

Для CPFD оферів відправляються лише ті гравці, які були кваліфіковані (по FD/RD постбекам).

2.7. Основний параметр для Postback URL – це Click_ID (get-параметр click_id у партнерському посиланні). Саме по ньмо відбувається зв'язок події з лідом, якого привів партнер.

2.8. Відмінність AMP_User_ID, Site_User_ID і POSTBACK_ID

[image: https://d295evyo48.ucarecd.net/4c0a2c8d-4a0e-4008-9bb7-4e7fa615b657/Group_7.png_2025-11-11_12-42-16.png]

- User (AMP_User_ID) – ID гравця на партнерці;
- Player (Site_User_ID) – ID гравця на сайті бренду (для різних брендів ID може співпадати);
- POSTBACK_ID – унікальний ID постбеку.

2.9. Відправка постбеків і помилки.

Успішно відправлений постбек – це 200-й код відповіді, який видно в системі.

Якщо отримуємо не 200-й код, вмикається алгоритм повторних відправлень:
перша спроба – через 5 хвилин, наступні – кожні 2 години. За замовчуванням постбек перевідправлятиметься до 5 разів.

Якщо після 5 спроб постбек потрібно відправити, можна URL із цим постбеком вбити в адресному рядку. Або ж вигрузити партнеру зафейлені постбеки, щоб він сам пропінгував їх.

Після 5 спроб постбек набуває статусу "Скасовано".

Додатково можна зменшити або відключити кількість відправки постбеку при наявності помилки.

[image: https://d295evyo48.ucarecd.net/d1315fdb-9181-4afb-8242-519a1d6818e6/image.png]

Можливість відключити повторну відправку для конкретного постбеку партнера знадобиться, якщо він нам сказав, що трекінг-система не працює, але попросив не видаляти їх та фіксить проблему, аби не сипалися алерти.

2.10. Відправка постбеку по гравцю, який здійснив подію до налаштування шаблону постбеку для партнера.

Платформа за поточний день згенерує постбек, якщо за гравцем під час реєстрації буде вказано click_id, оскільки відбувається перевірка при перерахунку всієї статистики на наявність постбеків. Стосується лише випадків день у день.

Важливо розуміти, що кейс є актуальним для випадків, якщо для партнера в той же день (після реєстрації гравця) було додано шаблон постбеку.

Кожні 5-15 хвилин відбувається автоматичний перерахунок за сьогодні, під час якого перевіряється вся статистика за поточний день.

Нюанси:

** Якщо за гравцем є click_id + статистика, АЛЕ гравець реєструвався раніше, а кваліфікований він був у день додавання шаблону постбеку (ДО його додавання), то буде згенеровано постбек події та постбек реєстрації, який завжди створюється і не залежить від дати реєстрації.

По гравцю будуть відправлені постбеки у відповідності з подією/подіями за той день + Реєстрація (REG), наприклад:

- Реєстрація (REG) + Перший депозит (FD);
- Реєстрація (REG) + Повторний депозит (RD);
- Реєстрація (REG) + Кваліфікація (CPA Hold);
- Реєстрація (REG) + Перший депозит (FD) + Кваліфікація (CPA Hold);
- Реєстрація (REG) + Підтвердження (CPA Approve) / Відмова (CPA Reject).

## 3. Тестування URL постбеків

3.1. На сторінці додавання/редагування шаблону можна протестувати URL кожної події постбеку. Доступне тестування з рандомним або реальним click_id. Функціонал дозволяє перевірити, чи працюють посилання, які надав партнер.

[image: https://d295evyo48.ucarecd.net/96ada6e8-ec26-4e87-8261-f60a030ea15b/image.png]

3.2. Перевірка (CLICK_ID рандомний)

При тестуванні CLICK_ID рандомний усі макроси, що підставлені в посилання, будуть рандомними. Наша система переходить за посиланнями й перевіряє код відповіді, який повернув сервер із трекером партнера.

Після натискання на "Перевірка (CLICK_ID рандомний)" стартує перевірка URL усіх подій постбеків із підстановкою рандомного click_id з нашого боку. При кожній перевірці генерується нове значення click_id.

[image: https://d295evyo48.ucarecd.net/9b0818fb-b993-4c54-b724-6da00937c2a0/screencast_2025-11-11_12-46-11.gif]

3.3. Якщо в URL використовуються макроси ##POSTBACK_ID## та ##TRANS_ID##, для них генерується рандомне значення в діапазоні [0 ; 10000].

Якщо в URL постбека використовуються інші макроси, для них підставляються потенційно можливі значення.

Список значень для кожного макроса:

- ##USER_ID## → 1
- ##IP_REG## → 1.1.1.1
- ##GEO_REG## → NL
- ##FD_AMOUNT## → 10
- ##RD_AMOUNT## → 10
- ##SITE_ID## → 1
- ##CPA_AMOUNT## → 10
- ##SUB_ID##, ##SUB_ID_2##, ##SUB_ID_3## , ##SUB_ID_4## , ##SUB_ID_5## → test
- ##RS_AMOUNT## → 10

Поруч з кожним івентом виводиться код відповіді сервера, який отримуємо в результаті переходу за URL постбека.

200-й код відповіді → означає, що перевірка пройшла успішно.

3.4. Перевірка (CLICK_ID реальний)

Тестування з click_id реальний необхідно, щоб партнер упевнився у правильній роботі інтеграції, при такому тестуванні він у себе в трекері побачить подію. Також є трекери, сервер яких відповідає 200-х кодом лише на click_id у посиланні, що було ним згенеровано.

Партнеру попередньо потрібно відправити реальний click_id для перевірки менеджеру.

Для перевірки вводимо існуючий click_id, його значення буде підставлено замість макросу ##CLICK_ID##. Усі інші значення будуть рандомними (описано вище).

Для модального вікна перевірки постбека доступний пункт "Подія". У випадаючому списку параметра відображаються всі події, для яких заповнено URL у шаблоні постбека. Можна обрати одразу всі події або лише конкретну.

[image: https://d295evyo48.ucarecd.net/daa4a1bb-22a6-4b7e-be39-f879dfa9ca55/image.png]

Якщо в межах шаблону постбека одночасно заповнені обидві події: "Підтвердження (CPA Approve)" та "Відмова (CPA Reject)", і при цьому вибрано значення "Всі", виводиться окремий пункт для вибору конкретної події для перевірки: "Підтвердження (тільки CPA)" або "Відмова (тільки CPA)".
За замовчуванням встановлено "Підтвердження (тільки CPA)".

Обидва заходи є взаємовиключними і не можуть перевірятися одночасно.

[image: https://d295evyo48.ucarecd.net/5864a2f0-5b2f-4698-9ee3-de9d7f865b49/screencast_2025-11-11_12-51-01.gif]

Якщо перевірка відбувається зі значенням "Всі", використовується поточна логіка перевірки, за якої вказаний click_id застосовується для перевірки всіх URL подій. При цьому враховується вибір між "Підтвердження (тільки CPA)" та "Відмова (тільки CPA)".

## 4. Сторінка "Лог усіх постбеків"

4.1. На сторінці "Лог усіх постбеків" виведено лог з інформацією по шаблонам постбеків партнерів.

Лог постбеків завантажується з фільтрацією по даті створення за поточний день, однак установку можна змінити у фільтрі.

Постбеки відправляються за UTC+0.

[image: https://d295evyo48.ucarecd.net/5afff0eb-8bae-479a-92de-7a185c4093f8/Group_8.png]

4.2. Для логу доступний пошук за:

- ID/Email;
- Офером (ID офера чи дефолтна назва в адмін-панелі);
- Click_ID.

4.3. На сторінці розміщено фільтри:

- Період створення;
- Локація;
- бренд;
- Група;
- Статус;
- Тип;
- Період кваліфікації;
- Період останньої спроби (період останньої спроби відправки постбека у межах шаблону).

Для фільтрації за періодом (створення, кваліфікації, останньої спроби) установлено обмеження в 31 день.

4.4. Можливий "Експорт", за допомогою якого експортується таблиця з виведеними даними. Кнопка "Експорт" знаходиться справа над таблицею.

4.5. Виведені в таблиці дані розподілено за стовпчиками:

- "ID" → ID постбека;
- "E-mail" → e-mail партнера. При натисненні на пошту відкривається сторінка "Профіль" партнера;
- "Бренд" → бренд, по якому відстукуємо постбек;
- "Офер" → офер, по якому відстукуємо постбек;
- "Дата створення" → дата створення постбеку;
- "Дата квал/деквал" → дата кваліфікації/декваліфікації;
- "Остання спроба" → дата й час останньої спроби відстукування постбеку;
- "Тип" → абревіатура типу постбеку, при наведенні на скорочення виводиться тултип з повною назвою типу постбеку;
- "Стат." → іконка статусу постбеку, при наведенні на іконку виводиться тултип з повним статусом;
- "Код відп." → код відповіді сервера трекера партнера по відстукуючому постбеку;
- User / Player» → ID гравця на партнерці, ID гравця на сайті бренду;
- "Click_ID → click_id постбеку.

Кнопки дії:

- Іконка "вічко" → при натисненні в поточній вкладці відкривається сторінка "Деталі постбеку";

[image: https://d295evyo48.ucarecd.net/57d5ae15-2a9d-4d80-9991-9cc11ea13f5a/Group_9.png]

- Іконка "хрестик" → хрестик виводиться лише поряд з постбеками, по яким можна скасувати відправлення, аналогічно логіці "Скасувати відправлення" (по помилковим або постбекам, що знаходяться в статусі "Очікує відправлення").

4.6. Розшифровка типів постбеку:

- REG – Реєстрація;
- FD – Перший депозит;
- RD – Повторний депозит;
- QCPA – Кваліфікація (за CPA);
- APRV – Підтвердження (за CPA);
- RJCT – Відмова (за CPA);
- AUTO – Автореджект реєстрацій/подій;
- APK – Інстал APK;
- RS – RevShare дохід.

4.7. Розшифровка статусів постбеку:

[image: https://d295evyo48.ucarecd.net/5d937cab-8012-4568-b358-af356722a18b/image.png]

- Не буде відправлено – (технічний статус) якщо у партнера вказано порожній URL для події, то постбек створиться, але відправлятися не буде;
- Скасовано – відправлення постбеку скасовано вручну. Або після 5 спроб постбек не був успішно відправлений (відповідь 200 не отримано) – функціонал повторного відправлення постбеків. У статусі "Скасовано" більше не буде спроб повторно відправити постбек;
- Очікує відправлення – статус постбеку при отриманні статистики;
- Відправлено – постбек відправлено;
- Помилка – постбек не вдалося відправити. Якщо для шаблону налаштовано кілька спроб повторного відправлення, статус "Помилка" буде присвоюватися до останньої спроби, після чого – "Скасовано";
- Auto-reject registered (внутрішній статус системи, доступний тільки для НЕ RS-оферів означає, що гравця більше не буде кваліфіковано через завершення періоду кваліфікації від дати реєстрації (відповідно до умов офера). Після цього статусу по конкретному гравцю партнеру більше не відправляються постбеки.
- Призупинено – відправку постбеків за шаблоном було призупинено.

Нюанси:

** Якщо постбек отримує статус "Скасовано" і в деталях постбека відображається код відповіді "Blocked domain", система робить лише 1 спробу надсилання постбека. Це пов'язано з особливістю обробки цієї помилки, оскільки повторні спроби недоцільні при заблокованому домені.

** При досягненні ліміту в 50 помилок для одного домену, подальші постбеки автоматично скасовуються, і спроби надсилання не виконуються, постбек отримує статус "Скасовано" і в деталях постбека відображається код відповіді "Blocked domain".
При наступній обробці даних (приблизно через годину) система перевіряє можливість надсилання нових постбеків. Якщо домен починає успішно відповідати, він автоматично видаляється зі списку заблокованих.

** Причиною того, що постбек не відправляється успішно, може бути недоступність трекера, блокування нашої IP-адреси трекером тощо. З нашого боку точна причина не визначається.

*** Перевірити IP-адресу, з якої надсилається постбек, можна в "Лозі постбеків" у будь-якому успішно надісланому постбеку в "Коді відповіді".

[image: https://d295evyo48.ucarecd.net/006f5c87-1b79-403b-ad88-7c11aa726bbf/blurred.png]

## 5. Деталі постбеку

5.1. Деталі постбеку – переходимо з "Логу усіх постбеків", на сторінці виводиться інформація з деталями щодо постбеку, партнера та гравця.

[image: https://d295evyo48.ucarecd.net/612333d6-4f55-4ce6-b78e-26208ef5a782/Group_10.png]

5.2. Блок з інформацією по партнеру містить дані: ID, E-mail, Менеджер партнера, Локація, Баланс партнера.

При натисненні на кнопку "У кабінет" відбувається вхід під партнером до К/П → "Увійти як".

На сторінці доступна можливість редагування міток для партнера.

Нижче блоку з інформацією по партнеру розташовано блок із даними по гравцю, якого привів партнер.

5.3. "Лог відправлення" складається з таблиці зі стовпчиками: Дата створення, Кількість спроб, Остання спроба, Тип, Статус, FD, RD, RS, URL (URL, по якому відстукували постбек), Код відповіді (код відповіді, що повернув сервер партнера за URL).

При наведенні на кнопку "Детальніше" в коді відповіді можна побачити повністю response сервера.

Щоб перевірити IP-адресу, з якої надсилається постбек, можна відкрити Код відповіді сервера на раніше успішно надісланий постбек. У ньому можна знайти значення поля local_ip.

### 6. Призупинення відправки постбеків у межах шаблону

6.1. Якщо виникають тимчасові проблеми з трекером партнера або з налаштуваннями шаблону, постбеки можна поставити на паузу та відновити їх після виправлення.

Функціонал "Призупинення" / "Активації" доступний лише в адмін-панелі.
У кабінеті партнера статус шаблону за Призупиненням / Активацією не відображається.

На сторінці "Шаблони постбеків" доступна кнопка дії "Призупинити".

[image: https://d295evyo48.ucarecd.net/7db19871-cf39-47d4-a0d3-2a03f8bad8c5/Снимок_экрана_2026-01-07_в_18.33.17.png]

Після кліку відкривається модальне вікно для підтвердження паузи в межах шаблону постбека.
Після призупинення постбеки за вибраним шаблоном не надсилатимуться в трекер партнера.

[image: https://d295evyo48.ucarecd.net/265e07cd-d660-4289-bac9-2a7adadc371a/AMP_-_Postback_Urls_2026-01-07_18-35-26.png]

Що відбувається з постбеками під час паузи:
Під час паузи постбеки не надсилаються та відображаються в лозі зі статусом "Призупинено".
Постбеки зберігаються до 7 днів. Після активації їх можна надіслати повторно.
Якщо пауза триває більше 7 днів, зберігаються лише останні 7 днів.

6.2. Для відновлення відправки постбеків натисніть "Активувати" та виберіть варіант:

- "Активувати та надіслати" – система відновить відправку постбеків за шаблоном і надішле всі постбеки зі статусом "Призупинено" за період паузи. Відправка здійснюється з датою та часом після активації.
- "Тільки активувати" – система відновить відправку постбеків без надсилання постбеків, створених зі статусом "Призупинено".

[image: https://d295evyo48.ucarecd.net/9204b7f3-5335-44e9-b5de-2c3c3a17db2c/Снимок_экрана_2026-01-07_в_18.37.07.png]

6.3. Призупинення та активація відправки постбеків зберігається в "Лозі змін шаблону".

[image: https://d295evyo48.ucarecd.net/8e5b739f-5dd6-4c67-8ed3-6bbfa6f1ee24/Снимок_экрана_2026-01-07_в_18.41.34.png]
