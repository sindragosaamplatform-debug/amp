## 2. Кастомні умови оферів

Для офера можна задати кастомну умову за ГЕО, Sub_ID або їх комбінацією.

У кастомній умові вказується: Країна, Значення основного Sub_ID, Ставка, Baseline (сума депозитів), Кількість спінів (раундів), Кількість депозитів.

[image: https://ucarecdn.com/a1ad7383-7f64-4c7d-8dc7-3c4761a4b276/screencast_2025-03-24_17-47-25.gif]

Одне з полів — "Країна" (ГЕО) або "Sub_ID" – обов’язкове для заповнення при додаванні кастомної умови.

Регістр символів у Sub_ID не враховується.
Якщо задати ставки для Sub_ID TEST і окремо для test, система сприйматиме їх як один і той самий Sub_ID.

Якщо потрібно налаштувати ставку лише за ГЕО, то в кастомних умовах поле Sub_ID залишаємо порожнім.

Поле Sub_ID підтримує роздільники: кома та Enter.

[image: https://d295evyo48.ucarecd.net/a628aa3f-9094-4cf9-9d3c-e4f0f9a56cc1/image.png]

Нюанси:

- Значення для Sub_ID не підтягується автоматично з уже створених у партнера – його вводимо вручну;
- Кілька значень Sub_ID додаються через кому. Пробіли при цьому не враховуються;
- Для RS оферів можна задавати кастомну умову тільки за країною (ГЕО);
- Кастомні умови недоступні для RS-частини в гібридних оферах, враховується лише CPA частина за кастомними умовами;

Пріоритет обробки умов всередині офера (від найвищого до найнижчого):
ГЕО + Sub_ID → Sub_ID → ГЕО → базові умови.

3. Опис полів офера

- CPA Ставка → Сума виплати партнеру.
- Бейслайн → Сума депозитів. Умова, за якої гравець має внести депозитів на суму, не меншу за встановлений бейслайн.
- Спіни → Кількість спінів, які користувач має зробити для проходження кваліфікації (якщо умова встановлена).
- Депозити → Умова проходження кваліфікації, за якої користувач має зробити вказану кількість депозитів.
Враховується загальна кількість депозитів, включно з першим (FD). Метрика — FD+RD count.
Значення "1" означає, що кваліфікація настає після першого депозиту. Якщо для кваліфікації потрібен щонайменше один повторний депозит (RD) – потрібно вказати значення "2".
- Дні для кваліфікації від реєстрації → Кількість днів, протягом яких гравець має виконати всі умови кваліфікації (Baseline, спіни, кількість депозитів). Час рахується з моменту реєстрації.
- Дні до автореджекту → Кількість днів після кваліфікації, через які кваліфіковані ліди будуть автоматично відхилені, якщо їх не було виведено з холду.
За цей період гравець має пройти перевірку відділом антифроду. Якщо по завершенню цього терміну гравець не пройшов перевірку, виплата за нього автоматично списується.
- Розраховувати CPA за EntryMonth → Якщо гравець зареєструвався в поточному місяці, а виконав умови кваліфікації в наступному – статистика по ньому не відображатиметься, і виплата не буде нарахована. Такий гравець не буде вважатися кваліфікованим.
Якщо гравець зареєстрований 30.06, а виконав умови кваліфікації 01.07 – він не зараховується.

Робота функціоналу "Розраховувати CPA за EntryMonth" описана детально в статті: https://help.aff.ltd/uk/admin-panel/entry-month-cpa

- Рівні дискваліфікації гравців → Рівні перевірки гравців на мультиакаунти. Глибина перевірки задається окремо для кожного оферу.

○ Рівень 1 – кількість мультиакаунтів із рефкодами заданого партнера на поточному бренді
○ Рівень 2 – кількість мультиакаунтів із рефкодами заданого партнера на всіх брендах партнерської програми (включно з ремаркетингом)
○ Рівень 3 – кількість мультиакаунтів з усіма рефкодами всіх партнерів на поточному бренді (включно з ремаркетингом)
○ Рівень 4 – кількість мультиакаунтів з усіма рефкодами всіх партнерів лише по брендах у межах партнерської програми партнера
○ Рівень 5 – кількість мультиакаунтів з усіма рефкодами всіх партнерів на всіх брендах усіх партнерських програм (включно з ремаркетингом)

- Ліміт для рівня декваліфікації гравця → Кількість мультиакаунтів одного гравця, мінімально достатня для його декваліфікації. Відображає рівень, при якому (>=) гравець не пройде кваліфікацію. Ліміт розраховується включно з гравцем, якого перевіряють. Мінімальне значення ліміту для перевірки – 2.
Ліміт: 2 – якщо у гравця є 1 мультиакаунт, він буде декваліфікований.
- Умови відключення декваліфікації (відсічка декваліфікації) → Умови відключення декваліфікації при збільшенні/зменшенні заздалегідь заданого параметра (Dequal %, Dep2Qual %).
- Revshare 1 (динамічна RS ставка 1) → Відсоток відчислень партнеру від програної суми гравця, якого він залучив.
- Revshare 2 (динамічна RS ставка 2) → Оновлена ставка по Revshare після досягнення другого порогу.
- Revshare 3 (динамічна RS ставка 3) → Оновлена ставка по Revshare після досягнення третього порогу.

Якщо партнер протягом місяця переходить на наступний рівень RS, а раніше відсоток був нарахований за першим порогом (RS нараховується кожен день), то після переходу на другий рівень проводяться донарахування по всіх попередніх нарахуваннях, які були розраховані за меншим порогом.

- Динамічна RS: Ліміт 1 → Кількість FD за місяць зі ставкою першого порогу.
- Динамічна RS: Ліміт 2 → Кількість FD за місяць для досягнення ставки по другому порогу.
- Динамічна RS: Ліміт 3 → Кількість FD за місяць для досягнення ставки по третьому порогу.

Наприклад:

Адмін-панель →
[Динамічна RS] Ставка 1: 25
[Динамічна RS] Ставка 2 = вмикається при досягненні ліміту 2: 35
[Динамічна RS] Ставка 3 = вмикається при досягненні ліміту 3: 45

[Динамічна RS] Ліміт 1 (кількість FD/місяць): до 45 FD
[Динамічна RS] Ліміт 2 (кількість FD/місяць): від 46 до 55 FD
[Динамічна RS] Ліміт 3 (кількість FD/місяць): від 56 FD

к/п →
0 - 45 FD – 25%
46 - 55 FD – 35%
56+ FD – 45%

Актуальні умови за Динамічними RS/CPA оферами виведені в к/п.

- CPA Ставка 1 = перша ставка по динамічному CPA → Перша ставка відчислень за динамічним офером.
CPA Ставка 2 = друга ставка по динамічному CPA → Ставка відчислень при досягненні другого порогу.
CPA Ставка 3 = третя ставка по динамічному CPA → Ставка відчислень при досягненні третього порогу.

Якщо партнер протягом дня по FD переходить на вищий рівень, то всі ліди за цю добу будуть нараховані за ставкою, на яку він перейшов.

- Ліміт 1 (кількість FD/добу) → Ліміт FD/добу на першому порозі відрахувань.
- Ліміт 2 (кількість FD/добу) → Ліміт FD/добу на другому порозі відрахувань.
- Ліміт 3 (кількість FD/добу) → Ліміт FD/добу на третьому порозі відрахувань.
- Дні для кваліфікації від FD (тільки для CPFD оферів) → Параметр визначає кількість днів для виконання умов кваліфікації з часу FD (першого депозиту).
- RentRef → Дозволяє налаштувати відчислення розробнику від доходу партнера за оренду його застосунку. У полі "Вебмастер" необхідно вибрати розробника застосунку, щоб він отримував відрахування за оренду застосунку. Fixed за Install нараховується вручну.

Видача офера партнеру для заливу через застосунок відбувається так само, як описано вище, але в налаштуванні необхідно вказати RentRef отримувача. Це розробник застосунку, яким користуватиметься партнер.
Попередньо розробник має зареєструватися в партнерській програмі, щоб з’явилася можливість вказати його ID у полі RentRef під час видачі офера.

3.1. Нюанси під час редагування відсічки декваліфікації

Відсічку декваліфікації (вимкнення декваліфікації) можна змінювати щогодини, але трафік, який "буде взято для перевірки вкл/викл відсічки", береться з початку дня, а не з моменту зміни.

- Статистика для визначення відсічки – за дату;
- Значення умов відсічки – останнє актуальне на дату.

Статистика розраховується окремо для кожного дня (з початку доби).

Наприклад: ми хочемо втримати конверсію партнера й не деквалити понад 10% гравців. Ставимо відсічку Dequal % – 10%. Серед усіх гравців за сьогодні – більше 10% не буде задеквалено.

Змінювати відсічку на початку дня чи наступної години – немає значення, умови діятимуть для всіх гравців за сьогодні.

Приклад №1 (відсічка декваліфікації): Маємо 20% деквали, ставимо 10%. Всі гравці, які були задеквалені раніше, так і залишаться задеквалені на рівні 20% (для розрахунку беремо кейс, де є 100 гравців, з них 20 – уже задеквалені).
Приходить ще 1 гравець, який має потрапити в деквалу,
але він не потрапляє, бо поточний рівень декваліфікації = 20%, а відсічка –10%.
Приходять ще 20 гравців, які також мали б бути задеквалені. Рівень деквали вже 11%, в умовах офера стоїть 10%. Ще кілька гравців перейдуть поточний рівень деквали, він стане 9%. Прийдуть нові гравці – вони задекваляться (до рівня 10%).

Важливо! Якщо в момент перерахунку надійде одразу велика кількість гравців, то вони можуть перевищити встановлений рівень у 10%, деквала може досягати, наприклад, 13% (це більше, ніж встановлено в офері, але вони задекваляться, і по відсічці знову відключиться спрацювання для наступних гравців).

Приклад №2: протягом дня хочемо тримати конверсію партнера за Dep2Qual % на рівні 20–30%.
○ О 10 ранку ставимо відсічку Dep2Qual % – 70%. Кваліфікуються не менше 30% гравців.
○ Об 11 (наступна година) за умовами змінюємо з 70% на 80%. Конверсія буде близько 20%.
○ О 12 (наступна година) змінюємо відсічку на 75%.

Таким чином щогодини можна регулювати конверсію для партнера.

Важливо! Хоч ми і змінюємо умови щогодини, у будь-якому разі вплив йде на всю масу гравців ЗА СЬОГОДНІ. Відсічка не буде змінювати і розкваліфіковувати вже наявний трафік.

4. Застосування редагування оффера

## Під час редагування CPA типів оферів зміни активуються:

- З початку поточної доби – зміни застосовуються до всіх гравців з початку поточної доби (00:01). Вони впливають як на гравців, які вже пройшли кваліфікацію, так і на тих, хто ще не кваліфікований.
- З 12:00 (з наступної години) – зміни застосовуються до гравців, у яких з’явиться статистика з наступної години, і які ще НЕ пройшли кваліфікацію.
- Вибрати дату і час (запланувати редагування) – зміни застосовуються до гравців, у яких з’явиться статистика з моменту запланованого застосування оффера, і які ще НЕ пройшли кваліфікацію.

Наприклад:

- З початку поточної доби: за умовами офера встановлено Baseline $10 і 30 спінів. Гравець о 9:00 зробив депозит $11 і виконав умови по спінах – система його кваліфікувала. Якщо о 15:00 змінити умови на Baseline $15 і застосувати «З початку поточної доби», гравець буде розкваліфікований.
- З наступної години: за умовами офера встановлено Baseline $10 і 30 спінів. Гравець о 9:00 зробив депозит $8 і виконав умови по спінах, але загалом умови оффера не виконав – система його НЕ кваліфікувала. Якщо о 15:00 змінити умови на Baseline $5 і застосувати «З наступної години», тоді, якщо нам надходить статистика о 17:00 і в ній є спіни по цьому гравцю (він продовжив грати), система його кваліфікує, оскільки орієнтуватиметься на умови офера на момент отримання статистики по цьому гравцю (на дату й час отримання статистики).

Актуально для всіх типів CPA-оферів (у тому числі для CPFD та CPA-частини в гібридних оферах).

[image: https://ucarecdn.com/20c9e486-26c8-4da0-b0ca-36fec18e6240/image.png]

Під час редагування відсотка RS в RS-оферах або в гібридних оферах, статистика – залежно від обраної умови редагування (з початку дня або з наступної години) – буде розраховуватись за новою ставкою.

Наприклад:
Змінюємо ставку для RS-офера з 20 на 30.
Є Гравець 1, який грає цілий місяць.
Ми видали офер 1 жовтня, а 27-го змінюємо умови з наступної години.
До моменту зміни всі нарахування по ньому будуть за ставкою 20%, після – вже за 30%.

5. Блокування офера

## Під час блокування офера весь трафік, який надходить на нього за партнерським посиланням, не відображається в статистиці кабінету партнера.

Нарахування на баланс партнера за такими оферами не здійснюються.

За заблокованим офером неможливо згенерувати посилання або відфільтрувати статистику.

Для партнера у к/п виведення статистики за заблокованим офером вмикається за допомогою чекбоксу "Виводити статистику за заблокованим офером в кабінеті партнера. Нарахування доходу не здійснюються.".

[image: https://ucarecdn.com/1a1bf0c6-a774-4a44-82f8-4378e29740ef/Снимок_экрана_2025-03-21_в_18.08.04.png]

5.1. Під час блокування офера умови будуть підтягуватись із шаблону офера. Аналогічним чином умови відображатимуться у к/п.

5.2. За посиланням на заблокований офер не формуються постбеки.

## 6. Пріоритетність роботи оферів для партнера

Пріоритетність оферів визначає порядок, у якому застосовуються різні рівні офера для виплат партнерам.

Рівні визначають, який офер матиме перевагу, якщо до конкретного партнера можуть бути застосовані кілька оферів:

- Кастомний офер партнера (має найвищий пріоритет).
- Офер для групи партнерів (встановлюється для певної групи партнерів).
- Базовий офер для групи партнерів (налаштовується в розрізі окремих партнерських програм, для яких він доступний).
- Дефолтний офер (застосовується за замовчуванням).

Якщо налаштовано кілька рівнів, пріоритет визначається зверху вниз.

Приклад:
Якщо в кастомному офері партнера (найвищий пріоритет) вказано 60% доходу від програшу, а в груповому офері (нижчий пріоритет) – 40%, партнер отримає 60%.
